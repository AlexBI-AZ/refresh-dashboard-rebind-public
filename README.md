# 📊 Power BI Dashboard Control Panel — руководство пользователя

## Что это такое

Панель управления для трёх независимых операций с Power BI / Fabric:

**Refresh** — обновление нескольких Dataflow, затем нескольких семантических моделей через Power BI REST API. Все dataflow запускаются вместе; модели запускаются вместе только после успешного завершения каждого dataflow. Для каждой модели показывается отдельный статус.

**Rebind** — замена GUID рабочих областей, dataflow и dataset в исходном коде PBIP-проекта. Сканирует `.tmdl` и `.json` файлы, находит старые GUID, заменяет их на новые и проверяет результат. Полный цикл: сканирование → понятное резюме → решение пользователя → замена → верификация. Работает с локальными файлами и не требует аутентификации.

**Rebind работает на любом компьютере с Windows** без прав администратора, дополнительных модулей или доступа к Power Automate. Для Refresh требования перечислены ниже.

**Partition Refresh** — точечное обновление одной или нескольких исторических партиций семантической модели через Power BI Enhanced Refresh API.

**Текущая версия интерфейса:** v0.5.0.

## Первый запуск

### 1. Что нужно для работы

- **PowerShell 5.1** (уже встроен в Windows 10/11)
- **MSAL.PS** — нужен только для аутентификации вкладки Refresh. Для Rebind он не требуется. При необходимости установите вручную:
  ```powershell
  Install-Module -Name MSAL.PS -Scope CurrentUser -Force
  ```
- Для Refresh: доступ к рабочей области Power BI / Fabric (роль Member или выше)
- Для Rebind: ничего дополнительно не нужно — работает с локальными файлами

### 2. Запуск

Дважды кликните файл **`launch.bat`**. Сервер и браузер откроются сразу, без запроса входа. Вкладка Rebind полностью готова к работе.

Если нужен Refresh, перейдите на вкладку Refresh и нажмите **«Authenticate for Refresh»**. Только после этого в консоли появится код устройства (device code):
```
To sign in, use a web browser to open the page https://login.microsoft.com/device
and enter the code ABC12DEFG to authenticate.
```

Перейдите по указанной ссылке, введите код и войдите под рабочей учётной записью Microsoft. Панель уже открыта; после успешного входа Refresh станет доступен.

### 3. Окно консоли

**Не закрывайте консольное окно!** Оно работает как сервер. Пока окно открыто, панель управления доступна в браузере по адресу `http://localhost:8765`. Закрытие окна останавливает сервер.

## Аутентификация и хранение токенов

### Как работает вход

Вход выполняется только по запросу вкладки Refresh. Сервер пытается получить токен доступа тремя способами (в порядке приоритета):

| Шаг | Метод | Описание |
|-----|-------|----------|
| 1 | Кэш MSAL | Встроенный кэш Windows Credential Manager. Если вы уже входили на этом компьютере через `setup-auth.ps1` или другой скрипт с тем же Client ID — токен находится мгновенно |
| 2 | Файл `.token` | Если кэш MSAL пуст, сервер проверяет сохранённый в прошлый раз токен в файле `.token`. Делает пробный запрос к API — если токен ещё жив, использует его |
| 3 | Device Code | Если оба способа не сработали и пользователь нажал «Authenticate for Refresh» — запрашивает новый вход через код устройства |

### Сколько живёт токен

- **Access-токен:** ~1 час. После входа через кнопку **«Authenticate for Refresh»** сохраняется в файл `.token`
- **Refresh-токен:** до 90 дней (в кэше MSAL). Если кэш MSAL работает на вашем компьютере — повторный вход не потребуется месяцами
- Если кэш MSAL **не** работает (зависит от конфигурации Windows) — вход потребуется примерно раз в час, когда истекает access-токен

### Важно для Rebind

Вкладка **Rebind не требует аутентификации** — она работает с локальными файлами. Сервер запускает браузер до любого входа, а предупреждение и статус аутентификации на вкладке Rebind скрыты.

### Совет

Чтобы закэшировать токен через MSAL, можно один раз запустить `setup-auth.ps1` или воспользоваться кнопкой на вкладке Refresh. Это никак не влияет на Rebind.

## Интерфейс

Интерфейс состоит из трёх вкладок: **Refresh**, **Partition Refresh** и **Rebind**. Переключение между ними — в верхней части экрана. У каждой вкладки своя боковая панель с профилями и своя форма.

## Partition Refresh

Вкладка отправляет Enhanced Refresh для точных имён таблицы и партиций. Имена партиций вводятся по одному на строку и не изменяются перед отправкой. Запрос всегда использует `type: full`, `commitMode: transactional` и Boolean `applyRefreshPolicy: false`; `notifyOption` не отправляется.

Перед отправкой показывается подтверждение с Workspace ID, Dataset ID, таблицей, всеми партициями и параметрами транзакции. Это реальная удалённая операция. После принятия запроса обработка продолжается в Power BI Service, даже если панель или компьютер отключатся. Проверка статуса и история используют только GET и никогда не повторяют POST.

Требуются MSAL.PS, права на семантическую модель и поддерживаемая Premium, PPU или Embedded capacity. Сочетание `status = Unknown` и `extendedStatus = InProgress` означает, что запрос выполняется нормально. При истечении аутентификации войдите снова для просмотра статуса; уже принятый запрос продолжит работу на сервере.

### Общие элементы

- **Верхняя панель:** текущее состояние (Idle / Running / Done / Failed); статус аутентификации показывается только на вкладке Refresh
- **Лог-панель:** в нижней части экрана отображает все события с временными метками. Логи для Refresh и Rebind накапливаются независимо — при переключении вкладок они сохраняются

## Вкладка Refresh

### Левая панель: профили

- **Список сохранённых профилей** — каждый профиль содержит Workspace ID dataflow, список Dataflow ID, список семантических моделей и настройки уведомления
- Клик по профилю — загружает его данные в форму справа
- Кнопка **«+ New»** — создать новый профиль
- Кнопка **«Delete»** — удалить выбранный профиль (с подтверждением)

### Правая панель: форма и управление

- **Profile name** — название профиля (например, «Finance refresh»)
- **Workspace ID** — GUID рабочей области
- **Dataflow IDs** — GUID потоков данных. Можно добавить несколько — нажмите **«+ Add Dataflow»**. Кнопка **✕** удаляет dataflow из списка
- **Semantic models** — одна или несколько пар Workspace ID + Dataset ID. Кнопки **+ Add Semantic Model** и **✕** добавляют и удаляют модели
- **Notify colleagues** — необязательные email-адреса через запятую или точку с запятой. Пробелы и дубликаты удаляются при сохранении/запуске
- **Dry run** — не отправляет письмо, а записывает получателей, тему и итоговые строки в refresh-лог

Кнопки:
- **«Start Refresh»** — запускает цепочку обновлений. Активна только когда есть аутентификация
- **«Save Profile»** — сохраняет текущие ID в список профилей

### Как работает цепочка Refresh

1. **Запуск всех dataflow одновременно** — сервер отправляет запрос на обновление каждого dataflow
2. **Ожидание завершения всех** — каждые 30 секунд проверяется статус каждого. Прогресс отображается: «Running (2/5)» — 2 из 5 завершены
3. **Строгий шлюз** — если хотя бы один dataflow завершился с ошибкой, семантические модели получают статус Skipped и не запускаются
4. **Параллельный запуск моделей** — после успеха всех dataflow запрос отправляется каждой семантической модели; затем все модели опрашиваются до завершения
5. **Независимый результат** — ошибка одной модели не прекращает опрос остальных; каждая получает собственный статус Succeeded/Failed
6. **Одно итоговое письмо** — после всей цепочки формируется HTML-сводка с временем, длительностью, workspace, результатом и короткой ошибкой каждого элемента

Старые профили с полем `DatasetId` поддерживаются: при загрузке оно автоматически превращается в список из одной семантической модели в том же workspace.

### Email: выбор механизма

Используется **Power Automate с HTTP trigger**. Текущий MSAL-токен выдан для Power BI API и не может быть отправлен в Microsoft Graph; Graph `sendMail` потребовал бы отдельный Graph-токен и согласие на `Mail.Send`. SMTP потребовал бы хранить отдельные учётные данные и часто блокируется политиками Microsoft 365. HTTP flow оставляет отправку почты внутри Microsoft 365 и добавляет только один секрет — URL trigger.

URL не сохраняется в профиле и не должен попадать в Git. Worker читает его только из переменной среды `REFRESH_EMAIL_WEBHOOK_URL`.

#### Настройка Power Automate flow

1. Создайте cloud flow с trigger **When an HTTP request is received**.
2. Вставьте JSON schema ниже.
3. Добавьте **Compose** с expression `join(triggerBody()?['recipients'], ';')`.
4. Добавьте Outlook action **Send an email (V2)**:
   - **To:** output шага Compose
   - **Subject:** `triggerBody()?['subject']`
   - **Body:** `triggerBody()?['htmlBody']` (HTML)
5. Сохраните flow и скопируйте HTTP POST URL.
6. Сохраните URL в пользовательской переменной среды и перезапустите `launch.bat`:

```powershell
[Environment]::SetEnvironmentVariable(
  'REFRESH_EMAIL_WEBHOOK_URL',
  'PASTE-YOUR-FLOW-POST-URL-HERE',
  'User'
)
```

Request schema:

```json
{
  "type": "object",
  "properties": {
    "recipients": {
      "type": "array",
      "items": { "type": "string" }
    },
    "subject": { "type": "string" },
    "htmlBody": { "type": "string" }
  },
  "required": ["recipients", "subject", "htmlBody"],
  "additionalProperties": false
}
```

Фактический POST содержит ровно эти три поля. Если список получателей пуст, email-шаг пропускается без сообщения. Ошибка flow записывается как WARNING и показывается в интерфейсе, но не меняет результат Refresh.

#### Безопасная проверка

Сначала укажите тестовый адрес и включите **Dry run**. После Refresh в логе появятся получатели, тема и строки сводки, но HTTP-запрос не выполняется. Затем снимите Dry run и проверьте один живой запуск на собственный адрес перед добавлением коллег.

### Индикаторы прогресса

Рядом с кнопкой Start Refresh расположены общие индикаторы и список моделей:

- **Dataflow** — точка загорается синим при запуске, показывает прогресс (N/M), становится зелёной при успехе, красной при ошибке
- **Semantic models** — общий индикатор этапа и отдельная строка Running/Succeeded/Failed для каждой модели

## Вкладка Rebind

### Что такое Rebind

Rebind заменяет GUID рабочих областей, dataflow и dataset в исходном коде PBIP-проекта. Это нужно, когда вы копируете проект между средами и ссылки в M-запросах или метаданных отчёта должны указывать на новые объекты.

**Где происходит замена:**
- `.tmdl` файлы семантической модели (блоки `source =` в партициях)
- `expressions.tmdl` (общие M-запросы)
- JSON-файлы отчёта (если GUID встречается в них)

Rebind рекурсивно проверяет **все** `.tmdl` и `.json` файлы. Исключаются только содержимое каталогов `.pbi/` и файл `cache.abf`. Поэтому любой другой TMDL/JSON-файл будет изменён, если в нём найден старый GUID.

### Левая панель: профили Rebind

- **Список сохранённых профилей** — каждый содержит путь к проекту и список маппингов (Old GUID → New GUID)
- Клик по профилю — загружает его данные в форму
- Кнопка **«+ New»** — создать новый профиль
- Кнопка **«Delete»** — удалить выбранный профиль

### Правая панель: форма Rebind

- **Profile name** — название профиля (например, «Dev → test»)
- **Report folder path** — полный путь к папке PBIP-проекта. Папка должна содержать `.pbip`, `.Report` или `.SemanticModel`
- **Mappings** — список пар Old GUID → New GUID. Для каждого маппинга:
  - **Type** — выпадающий список: Workspace, Dataflow или Dataset
  - **Old GUID** — старый GUID (который нужно заменить)
  - **New GUID** — новый GUID (на который заменить)
  - Кнопка **⇄** — поменять местами Old GUID и New GUID
  - Кнопка **✕** — удалить маппинг
  - Валидация: зелёная рамка = корректный GUID, красная = некорректный
- Кнопка **«+ Add Mapping»** — добавить новую пару GUID

Состояние маппингов сохраняется в localStorage браузера и не теряется при перезапуске.

Сервер дополнительно проверяет входные данные: отклоняет одинаковые Old/New GUID, повторяющиеся Old GUID и цепочки, где New GUID одного маппинга используется как Old GUID другого. Цепочки нужно выполнять отдельными запусками Rebind.

### Рабочий процесс (две кнопки)

#### Шаг 1 — Scan (Фаза 1, только чтение)

Нажмите **«Scan»**. Сервер запускает фоновый worker, который:

1. Находит все `.tmdl` и `.json` файлы в проекте (исключая `.pbi/`)
2. Для каждого маппинга ищет все вхождения OLD GUID
3. Показывает до 2 строк с совпадениями для каждого файла
4. Проверяет, нет ли NEW GUID уже в проекте (частичная миграция)
5. Отмечает неоднозначные контексты (GUID в нестандартных файлах)
6. Сохраняет результаты для следующего шага

**Фаза Scan не вносит изменений в проект.** Просмотрите технический лог и понятное резюме. Если совпадений нет, Apply останется недоступным.

#### Шаг 2 — Apply (Фазы 2+3, замена и верификация)

После успешного Scan выберите **«Continue with Apply»** в резюме (или кнопку **«Apply»**). Отдельного диалога подтверждения нет: резюме Scan является точкой принятия решения.

Перед запуском сервер проверяет, что путь и маппинги не изменились после Scan. Любое изменение формы аннулирует результат Scan и требует повторного сканирования. Одновременно может выполняться только одна операция Rebind.

После продолжения worker:
1. Последовательно заменяет каждый OLD GUID → NEW GUID во всех затронутых файлах
2. Обрабатывает маппинги по одному; потенциально опасные цепочки отклоняются до запуска
3. После замены выполняет верификацию: проверяет, что старых GUID не осталось
4. Подсчитывает новые GUID и показывает результаты в техническом логе и итоговом резюме

Если выбрать **«Do not continue»**, сервер аннулирует Scan, проект остаётся без изменений, а для последующего Apply потребуется новый Scan.

### Индикаторы фаз

Рядом с кнопками Scan и Apply расположены три точки-индикатора:

- **Scan** — синяя при сканировании, зелёная при завершении
- **Replace** — синяя при замене
- **Verify** — зелёная при успешной верификации, красная при ошибке

### Логи Rebind

Подробный журнал Rebind отображается в браузере и хранится в `rebind-status.json` только для текущего состояния операции. Стандартный вывод ошибок фонового worker дополнительно перенаправляется в `logs/rebind-worker-errors.log`.

### Понятное резюме и решение

Технический лог остаётся без изменений. После Scan под ним появляется отдельная карточка с количеством просмотренных и затронутых файлов, предполагаемых замен и предупреждений. Пользователь явно выбирает **«Continue with Apply»** или **«Do not continue»**. Если выбрать остановку, Scan остаётся операцией только для чтения и проект не изменяется. После Apply та же карточка показывает итог замены и верификации простыми словами.

### После Rebind

Откройте отчёт в Power BI Desktop и обновите данные чтобы подтвердить соединение с источниками. Панель управления не может проверить живое соединение.

## Как это работает внутри

### Refresh

1. При нажатии **«Start Refresh»** сервер проверяет ID/email и передаёт worker закодированный JSON с dataflow, семантическими моделями и настройками уведомления
2. Создаётся временный скрипт `_worker.ps1`
3. Скрипт запускается в скрытом фоновом процессе
4. Worker вызывает Power BI REST API для параллельного запуска обновления всех dataflow
5. Каждые 30 секунд проверяет статус каждого dataflow через API транзакций
6. После успешного завершения всех dataflow — запускает все семантические модели
7. Каждые 30 секунд проверяет каждую модель до отдельного конечного результата
8. Строит итоговый HTML в `refresh-email.ps1` и при необходимости отправляет его в Power Automate flow
9. Весь прогресс записывается в `refresh-status.json`, который читается фронтендом

### Rebind — Scan

1. При нажатии **«Scan»** сервер проверяет PBIP-путь и маппинги, создаёт подпись запроса и генерирует `_rebind-worker.ps1`; параметры передаются worker в закодированном JSON
2. Worker сканирует все TMDL/JSON файлы проекта на наличие старых GUID
3. Для каждого совпадения записывает файл, номер строки и контекст
4. Результаты сохраняются в `rebind-status.json`

### Rebind — Apply

1. При нажатии **«Apply»** сервер сверяет путь и маппинги с подписью последнего Scan и генерирует новый `_rebind-worker.ps1`
2. Worker заменяет старые GUID на новые во всех затронутых файлах (точное совпадение, case-insensitive)
3. После замены запускает верификацию — перепроверяет все файлы
4. Результаты (какие файлы изменены, сколько замен) записываются в статус

## Настройка таймингов

### Refresh: интервал проверки статуса (сейчас 30 секунд)

В `_refresh-worker-template.ps1` найдите строки:
```powershell
Start-Sleep -Seconds 30
```
Замените `30` на нужное значение. Таких строк две: одна для dataflow, одна для семантических моделей.

### Refresh: максимальное время ожидания (сейчас 11 часов)

В том же файле найдите строки:
```powershell
if ($stopwatch.Elapsed.TotalHours -gt 11) {
    # Незавершённые элементы получают Failed
}
```
Замените `11` на нужное количество часов.

### Rebind

Таймингов нет — операции выполняются локально без задержек. Время зависит от размера проекта и количества файлов.

### Важно

После редактирования необходимо перезапустить сервер (закрыть консольное окно и снова открыть `launch.bat`).

## Использование и публикация на GitHub

Репозиторий безопасен для публикации, если в Git попадает только содержимое репозитория. Локальные профили, пути к PBIP-проектам, workspace/dataset/dataflow ID, email-адреса получателей, access-токен, логи и статусы исключены через `.gitignore`.

1. Клонируйте репозиторий на компьютер коллеги
2. Запустите `launch.bat` — Rebind откроется сразу без входа и дополнительных модулей
3. Только если нужен Refresh, установите MSAL.PS:
   ```powershell
   Install-Module -Name MSAL.PS -Scope CurrentUser -Force
   ```
4. Для Refresh: коллега нажимает «Authenticate for Refresh» или запускает `setup-auth.ps1`
5. Каждый пользователь создаёт свои локальные профили через интерфейс. Они сохраняются рядом с приложением, но не отслеживаются Git.

### Email flow и секреты

`REFRESH_EMAIL_WEBHOOK_URL` — секрет уровня bearer token. Не добавляйте URL Power Automate flow в код, профили, `.env.example`, README, issues или GitHub Actions. Каждый пользователь задаёт его только в своей переменной среды.

Один общий URL может использоваться командой, но его следует хранить как секрет и обслуживать в централизованном flow с ограничениями получателей. Для большей изоляции каждый пользователь может создать собственный flow. Если URL раскрыт, немедленно пересоздайте trigger URL в Power Automate и замените локальные переменные среды.

Перед первым push выполните `powershell -ExecutionPolicy Bypass -File .\release-check.ps1`. Скрипт проверяет, что рядом с проектом нет локальных профилей, токенов, `.env`, логов, status-файлов, а в исходниках — workspace/dataset/dataflow ID и Power Automate trigger URL. Затем проверьте `git status`.

**Не нужно:** прав администратора, установки Python/Node.js или Docker. Power Automate нужен только для живых email-уведомлений; Refresh без получателей и email dry run работают без него.

## Типичные проблемы

| Проблема | Решение |
|----------|---------|
| Браузер открывается, но страница не грузится | Подождите 5 секунд — сервер запускается не мгновенно. Обновите страницу |
| «Not Authenticated» на вкладке Refresh | Нажмите «Authenticate for Refresh» и завершите вход по коду из консоли |
| Аутентификация недоступна, но нужен только Rebind | Ничего устанавливать не нужно — перейдите на вкладку Rebind |
| Ошибка «Dataflow refresh FAILED» | Проверьте роль в рабочей области (нужен Member или выше). Проверьте правильность ID |
| Ошибка 404 или UnknownError | Dataflow или Dataset не найдены. Проверьте ID в профиле |
| Код устройства не появляется | Проверьте интернет-соединение. Убедитесь, что MSAL.PS установлен |
| Refresh: статус «Starting...» и ничего не происходит | Worker не запустился. Проверьте `logs\worker-start.log` и `logs\refresh-worker-errors.log` |
| «A refresh is already running» | Дождитесь завершения текущего обновления или перезапустите сервер |
| Email warning: webhook not configured | Задайте пользовательскую переменную `REFRESH_EMAIL_WEBHOOK_URL` и полностью перезапустите `launch.bat`, либо включите Dry run |
| Refresh успешен, email завершился ошибкой | Результат Refresh сохранён. Проверьте URL trigger и историю запусков flow; ошибка письма намеренно не меняет результат обновления |
| Rebind: Scan не запускается | Проверьте консоль сервера и убедитесь, что выбрана папка PBIP с `.pbip`, `.Report` или `.SemanticModel` |
| Rebind: кнопка Apply неактивна | Выполните Scan и используйте «Continue with Apply» в резюме. Если путь или GUID изменены после Scan, сканирование нужно повторить |
| Rebind: ошибка про chained mappings | New GUID одного маппинга совпадает с Old GUID другого. Разделите замену на два отдельных запуска |
| Rebind: GUID не найден при сканировании | Проверьте правильность GUID и что проект действительно PBIP (с файлами .tmdl) |
| Rebind: после Apply старые GUID остались | Проверьте логи — там указано в каких файлах и строках остались GUID |
| Порт 8765 занят | Закройте другой экземпляр или запустите `powershell -ExecutionPolicy Bypass -File .\server.ps1 -Port 8877`. Интерфейс автоматически использует текущий адрес и порт |
| Иконка вкладки браузера пустая | Нажмите Ctrl+Shift+R для очистки кэша браузера |
| MSAL.PS не установлен | Он нужен только для Refresh. Установите вручную: `Install-Module -Name MSAL.PS -Scope CurrentUser -Force` |
