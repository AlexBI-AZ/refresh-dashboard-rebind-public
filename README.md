# 📊 Power BI Dashboard Control Panel - руководство пользователя

## Что это такое

Панель управления для трех независимых операций с Power BI / Fabric:

**Refresh** - обновление нескольких Dataflow, затем нескольких семантических моделей через Power BI REST API. Все dataflow запускаются вместе; модели запускаются вместе только после успешного завершения каждого dataflow. Для каждой модели показывается отдельный статус.

**Rebind** - замена GUID рабочих областей, dataflow и dataset в исходном коде PBIP-проекта. Сканирует `.tmdl` и `.json` файлы, находит старые GUID, заменяет их на новые и проверяет результат. Полный цикл: сканирование → понятное резюме → решение пользователя → замена → верификация. Работает с локальными файлами и не требует аутентификации.

**Rebind работает на любом компьютере с Windows** без прав администратора, дополнительных модулей или доступа к Power Automate. Для Refresh требования перечислены ниже.

**Partition Refresh** - точечное обновление одной или нескольких исторических партиций семантической модели через Power BI Enhanced Refresh API.

**Текущая версия интерфейса:** v0.5.0.

## Установка

Права администратора, Python, Node.js и Docker не нужны. Нужен Windows 10 или 11 со встроенным Windows PowerShell 5.1.

1. Нажмите правой кнопкой на ZIP-архив, выберите **Свойства**, отметьте **Разблокировать** (Unblock) и нажмите **OK**. Иначе Windows считает каждый файл скачанным из интернета.
2. Распакуйте архив в постоянную папку, например `Documents\Power BI Control Panel`. Ярлыки будут указывать на нее.
3. Дважды кликните **`setup.bat`**. Он:
   - снимает блокировку с файлов папки, проверяет Windows PowerShell 5.1 и Microsoft Edge;
   - устанавливает модуль MSAL.PS для текущего пользователя, без вопросов про NuGet и PSGallery;
   - настраивает вход через device code. Только если на компьютере уже настроен рабочий сертификат (см. раздел «Аутентификация»), setup предлагает использовать его; ответ «n» переключает компьютер на device code. Сертификаты setup не создает;
   - один раз спрашивает URL flow Power Automate для писем (ввод скрыт; Enter пропускает шаг) и сохраняет его только в пользовательской переменной `REFRESH_EMAIL_WEBHOOK_URL`, не в файле;
   - создает ярлыки «Power BI Control Panel» на рабочем столе и в меню «Пуск»;
   - проверяет готовность, ничего не меняя (Ready или Not ready с причинами), и открывает панель.
4. На вкладке Refresh нажмите **«Authenticate for Refresh»**, откройте `https://login.microsoft.com/device` и введите код из окна консоли. Вход сохраняется, и повторять его обычно не нужно месяцами.
5. Создайте профиль: **New profile**, выберите рабочую область и отчет или модель по названию, затем **Save Profile**.

`setup.bat` можно запускать повторно: он меняет только то, чего не хватает. `setup.bat -CheckOnly` только проверяет готовность, `setup.bat -DryRun` показывает, что было бы изменено, и ничего не меняет.

Дальше панель запускается ярлыком (или `launch-app.bat`): отдельное окно Edge без адресной строки, консоль сервера свернута. Закрытие последнего окна панели останавливает сервер; повторный запуск при открытой панели открывает еще одно окно. Окно использует свой профиль Edge в `%LOCALAPPDATA%\PowerBIControlPanel\EdgeAppProfile`, без входа в учетную запись и синхронизации. Если Edge не найден, панель откроется в браузере по умолчанию. `launch.bat` запускает сервер в видимой консоли и открывает обычный браузер; эту консоль нельзя закрывать, пока панель нужна.

Rebind не требует входа и MSAL.PS.

## Аутентификация и хранение токенов

### Как работает вход

Весь вход для Refresh и Partition Refresh идет через один модуль, `runtime\powerbi-auth.ps1`. Им же runner продлевает токен во время долгого обновления, поэтому одно обновление никогда не меняет учетную запись посередине. Агент (Claude, Codex) для этого не нужен.

Есть два равноправных способа входа. По умолчанию используется device code; сертификат `setup.bat` предлагает только там, где он уже настроен:

| Способ | Для кого | Как настроить |
|--------|----------|---------------|
| Device code | Для тех, кто запускает обновления вручную. Вход под своей учетной записью: свои права на рабочие области, свое имя в журнале обновлений | Ничего настраивать не нужно. Нажмите «Authenticate for Refresh» и введите код из консоли на `https://login.microsoft.com/device`. Вход хранится в зашифрованном кэше `%LOCALAPPDATA%\PowerBIChainedRefresh\msalcache.bin3` |
| Сертификат (service principal) | Для компьютеров, где обновления идут без участия человека | Настраивается отдельно, не через `setup.bat`: сертификат с закрытым ключом в `Cert:\CurrentUser\My` и пользовательские переменные `POWERBI_REFRESH_TENANT_ID`, `POWERBI_REFRESH_CLIENT_ID`, `POWERBI_REFRESH_CERT_THUMBPRINT`; открытую часть сертификата владелец приложения загружает в регистрацию приложения. Если такой сертификат уже работает на компьютере, `setup.bat` предлагает использовать его. Приложение должно быть участником (Member) рабочих областей из профилей |

Правило выбора: переменная `POWERBI_REFRESH_AUTH_MODE` (`delegated` или `service-principal`) задает способ явно. Без нее используется сертификат, если заданы три переменные сертификата, иначе device code. Способ виден на значке входа в панели и в ответе `/api/auth/status` (поле `authMode`).

Закрытый ключ сертификата не покидает компьютер, на котором он создан: файл `.pfx` никто не копирует и не пересылает. Все сертификаты одного приложения входят под одним именем приложения и видят все рабочие области, к которым у приложения есть доступ.

Файл `.token` больше не используется; старый файл можно удалить.

### Сколько живет токен

- **Access-токен:** около 1 часа. Сервер получает новый каждые 40 минут, runner тоже продлевает его каждые 40 минут.
- **Device code:** повторный вход обычно не нужен месяцами, пока действует refresh-токен в кэше.
- **Сертификат:** вход не нужен, пока действует сертификат (дата окончания видна в `Cert:\CurrentUser\My` и в `setup.bat -CheckOnly`).

### Важно для Rebind

Вкладка **Rebind не требует аутентификации** - она работает с локальными файлами. Сервер запускает окно до любого входа, а предупреждение и статус аутентификации на вкладке Rebind скрыты.

## Интерфейс

Интерфейс состоит из трех вкладок: **Refresh**, **Partition Refresh** и **Rebind**. Переключение между ними - в верхней части экрана. У каждой вкладки своя боковая панель с профилями и своя форма.

## Partition Refresh

Вкладка отправляет Enhanced Refresh для точных имен таблицы и партиций. Имена партиций вводятся по одному на строку и не изменяются перед отправкой. Запрос всегда использует `type: full`, `commitMode: transactional` и Boolean `applyRefreshPolicy: false`; `notifyOption` не отправляется.

Рабочая область и семантическая модель выбираются поиском по названию; их GUID лежат в свернутом разделе **IDs**. Перед отправкой показывается подтверждение с названиями и ID рабочей области и модели, таблицей, всеми партициями и параметрами транзакции. Это реальная удаленная операция. После принятия запроса обработка продолжается в Power BI Service, даже если панель или компьютер отключатся. Проверка статуса и история используют только GET и никогда не повторяют POST.

Требуются MSAL.PS, права на семантическую модель и поддерживаемая Premium, PPU или Embedded capacity. Сочетание `status = Unknown` и `extendedStatus = InProgress` означает, что запрос выполняется нормально. При истечении аутентификации войдите снова для просмотра статуса; уже принятый запрос продолжит работу на сервере.

### Общие элементы

- **Верхняя панель:** текущее состояние (Idle / Running / Done / Failed); статус аутентификации показывается только на вкладке Refresh
- **Лог-панель:** в нижней части экрана отображает все события с временными метками. Логи для Refresh и Rebind накапливаются независимо - при переключении вкладок они сохраняются

## Вкладка Refresh

### Левая панель: профили

- **Список сохраненных профилей** - каждый профиль содержит рабочую область, семантические модели, dataflow и настройки уведомления. В карточке показано название рабочей области (после входа), а не ее GUID
- Клик по профилю - загружает его данные в форму справа
- Кнопка **«+ New»** - создать новый профиль
- Кнопка **«Delete»** - удалить выбранный профиль (с подтверждением)

### Правая панель: форма и управление

- **Profile name** - название профиля (например, «Sales Production»)
- **Workspace** - поиск рабочей области по названию: начните вводить часть названия и выберите из списка (стрелки и Enter тоже работают). Здесь же ищутся отчеты, модели и dataflow. В одном профиле можно смешивать объекты из разных рабочих областей
- **Semantic models** - поле «Add a report or semantic model» ищет отчеты и модели выбранной рабочей области. При выборе отчета добавляется его модель, а dataflow, из которых она читает данные, находятся по lineage и добавляются автоматически (под полем появляется сообщение, сколько найдено). Модель, которую нельзя обновить (DirectQuery или live connection), не добавляется. Кнопка **✕** убирает строку
- **Dataflows** - список с названиями и рабочими областями. Поле «Add a dataflow» добавляет dataflow выбранной рабочей области вручную, **✕** убирает строку
- **Model only** - обновить только семантические модели профиля, без dataflow. Действует на один запуск: dataflow остаются в профиле (их строки становятся бледными), флажок не сохраняется и сбрасывается при выборе другого профиля. Профиль без dataflow запускается в этом режиме и без флажка
- **IDs and manual entry** (свернутый раздел внизу формы) - Workspace ID и добавление dataflow или модели по GUID, если удобнее вставить ID. Названия для них подтягиваются автоматически

Для поиска по названиям нужен вход (сертификат или вход в панели). Поиск только читает данные Power BI и ничего не меняет. В профиле по-прежнему хранятся ID (переименование ничего не ломает), а рядом сохраняются названия для отображения. Старые профили без названий показывают их после входа, файл профилей при этом не меняется, пока вы не нажмете **Save Profile**. Если профиль сохранен в старом поврежденном формате (строки моделей вида `@{WorkspaceId=...; DatasetId=...}`), панель читает их и просит один раз сохранить профиль.
- **Notify colleagues** - необязательные email-адреса через запятую или точку с запятой. Пробелы и дубликаты удаляются при сохранении/запуске
- **Dry run** - не отправляет письмо, а записывает получателей, тему и итоговые строки в refresh-лог

Кнопки:
- **«Start Refresh»** - запускает цепочку обновлений. Активна только когда есть аутентификация
- **«Save Profile»** - сохраняет текущие ID в список профилей

### Как работает цепочка Refresh

1. **Запуск всех dataflow одновременно** - сервер отправляет запрос на обновление каждого dataflow
2. **Ожидание завершения всех** - каждые 30 секунд проверяется статус каждого. Прогресс отображается: «Running (2/5)» - 2 из 5 завершены
3. **Строгий шлюз** - если хотя бы один dataflow завершился с ошибкой, семантические модели получают статус Skipped и не запускаются
4. **Параллельный запуск моделей** - после успеха всех dataflow запрос отправляется каждой семантической модели; затем все модели опрашиваются до завершения
5. **Независимый результат** - ошибка одной модели не прекращает опрос остальных; каждая получает собственный статус Succeeded/Failed
6. **Проверка до и после** - перед запуском снимается состояние каждой модели, после обновления оно снимается снова и сравнивается. Если для модели есть конфиг отчета в `validation\reports\` (совпадают workspace и имя модели), используются его проверки. Иначе применяются универсальные проверки из `validation\universal-checks.json`: число строк в каждой таблице (предупреждение при изменении на 10%, ошибка при 25% или если таблица опустела) и структура модели (таблицы, столбцы, меры, связи). Проверка, которая не смогла выполниться, не останавливает обновление: в письме будет указана причина. Важно: снимок до берется уже после развертывания, поэтому влияние самого деплоя он не покажет; для этого первый запуск после деплоя сравнивают с прогоном до него через `-BaselineRunsBack` (см. `validation\README.md`).
7. **Одно итоговое письмо** - после всей цепочки отправляется одно письмо: карточка обновления (время, длительность, статус и ошибка каждого элемента) и раздел проверки для каждой модели. Копия письма сохраняется в папке запуска как `email.html` (или `email-preview.html` при Dry run)

С флажком **Model only** шаги 1-3 пропускаются: сразу запускаются семантические модели. Запрет одновременного обновления действует и здесь: если модель уже обновляется в сервисе, запуск отклоняется.

Старые профили с полем `DatasetId` поддерживаются: при загрузке оно автоматически превращается в список из одной семантической модели в том же workspace.

### Email: выбор механизма

Используется **Power Automate с HTTP trigger**. Текущий MSAL-токен выдан для Power BI API и не может быть отправлен в Microsoft Graph; Graph `sendMail` потребовал бы отдельный Graph-токен и согласие на `Mail.Send`. SMTP потребовал бы хранить отдельные учетные данные и часто блокируется политиками Microsoft 365. HTTP flow оставляет отправку почты внутри Microsoft 365 и добавляет только один секрет - URL trigger.

URL не сохраняется в профиле и не должен попадать в Git. Worker читает его только из переменной среды `REFRESH_EMAIL_WEBHOOK_URL`.

#### Настройка Power Automate flow

1. Создайте cloud flow с trigger **When an HTTP request is received**. В поле **Who can trigger the flow?** выберите **Any user in my tenant** (рекомендуется, см. «Кто может вызвать flow» ниже) или **Anyone**.
2. Вставьте JSON schema ниже.
3. Добавьте **Compose** с expression `join(triggerBody()?['recipients'], ';')`.
4. Добавьте Outlook action **Send an email (V2)**:
   - **To:** output шага Compose
   - **Subject:** `triggerBody()?['subject']`
   - **Body:** `triggerBody()?['htmlBody']` (HTML)
5. Сохраните flow и скопируйте HTTP POST URL.
6. Запустите `setup.bat` и вставьте URL, когда он спросит (ввод скрыт). URL сохраняется только в пользовательской переменной среды. Вручную то же самое делает команда:

```powershell
[Environment]::SetEnvironmentVariable(
  'REFRESH_EMAIL_WEBHOOK_URL',
  'PASTE-YOUR-FLOW-POST-URL-HERE',
  'User'
)
```

Request schema:

```json
{
  "type": "object",
  "properties": {
    "recipients": {
      "type": "array",
      "items": { "type": "string" }
    },
    "subject": { "type": "string" },
    "htmlBody": { "type": "string" }
  },
  "required": ["recipients", "subject", "htmlBody"],
  "additionalProperties": false
}
```

Фактический POST содержит ровно эти три поля. Если список получателей пуст, email-шаг пропускается без сообщения. Ошибка flow записывается как WARNING и показывается в интерфейсе, но не меняет результат Refresh.

#### Кто может вызвать flow

Настройка trigger **Who can trigger the flow?** определяет, как flow проверяет вызов. `refresh-email.ps1` поддерживает все три варианта:

| Who can trigger the flow? | Как панель вызывает flow | Кто может отправить письмо через flow |
|---|---|---|
| **Any user in my tenant** | POST на URL без ключа, с заголовком `Authorization: Bearer` и токеном Power Automate (audience `https://service.flow.microsoft.com/`) | Только вошедший пользователь или приложение вашего tenant |
| **Specific users in my tenant** | Так же, как выше | Только перечисленные пользователи и приложения. При входе по сертификату в список нужно добавить само приложение (его service principal) |
| **Anyone** | POST на URL как есть, без токена | Любой, у кого есть URL: ключ `sig` в URL и есть пароль |

Как это работает:

- Токен Power Automate получается тем же входом, что и обновление: при входе по коду устройства (device code) он берется из того же кэша MSAL без нового окна входа, при входе по сертификату запрашивается app-only токен того же приложения. Токен запрашивается только тогда, когда flow его требует, хранится только в памяти и не пишется в логи и файлы.
- URL без параметра `sig` сразу отправляется с токеном. URL с `sig` отправляется как есть. Если flow отвечает 401 или 403 (например, trigger переключили на **Any user in my tenant**, а в `setup.bat` остался старый URL), запрос повторяется один раз с токеном и без ключевых параметров `sp`, `sv`, `sig`: ключ и токен в одном вызове flow отклоняет. При 401 и 403 flow не запускается, поэтому письмо не уходит дважды.
- Токен отправляется только по HTTPS и только на адреса Power Automate (`*.logic.azure.com`, `*.api.powerplatform.com`). Для другого адреса письмо завершается ошибкой, токен не запрашивается.
- Так же отправляют письмо Claude-скилл `powerbi-chained-refresh` и проверенный запуск (`validation\Invoke-ValidatedRefresh.ps1`): они используют тот же `refresh-email.ps1` и тот же вход.
- Если tenant не разрешает этому входу получить токен Power Automate без согласия администратора, письмо завершается ошибкой с объяснением (результат Refresh не меняется). Тогда оставьте **Anyone** и ограничьте flow: проверка домена получателей, ограничение числа получателей, **Schema Validation** в настройках trigger.

После смены настройки trigger сохраните flow, скопируйте URL заново и запустите `setup.bat` с ним. Если в новом URL остался ключ `sig`, панель все равно отправит письмо: первая попытка будет отклонена, вторая уйдет с токеном.

#### Безопасная проверка

Сначала укажите тестовый адрес и включите **Dry run**. После Refresh в логе появятся получатели, тема и строки сводки, но HTTP-запрос не выполняется. Затем снимите Dry run и проверьте один живой запуск на собственный адрес перед добавлением коллег.

### Индикаторы прогресса

Рядом с кнопкой Start Refresh расположены общие индикаторы и список моделей:

- **Dataflow** - точка загорается синим при запуске, показывает прогресс (N/M), становится зеленой при успехе, красной при ошибке. При запуске Model only точка остается серой с подписью «Dataflow (skipped)»
- **Semantic models** - общий индикатор этапа и отдельная строка Running/Succeeded/Failed для каждой модели

## Вкладка Rebind

### Что такое Rebind

Rebind заменяет GUID рабочих областей, dataflow и dataset в исходном коде PBIP-проекта. Это нужно, когда вы копируете проект между средами и ссылки в M-запросах или метаданных отчета должны указывать на новые объекты.

**Где происходит замена:**
- `.tmdl` файлы семантической модели (блоки `source =` в партициях)
- `expressions.tmdl` (общие M-запросы)
- JSON-файлы отчета (если GUID встречается в них)

Rebind рекурсивно проверяет **все** `.tmdl` и `.json` файлы. Исключаются только содержимое каталогов `.pbi/` и файл `cache.abf`. Поэтому любой другой TMDL/JSON-файл будет изменен, если в нем найден старый GUID.

### Левая панель: профили Rebind

- **Список сохраненных профилей** - каждый содержит путь к проекту и список маппингов (Old GUID → New GUID)
- Клик по профилю - загружает его данные в форму
- Кнопка **«+ New»** - создать новый профиль
- Кнопка **«Delete»** - удалить выбранный профиль

### Правая панель: форма Rebind

- **Profile name** - название профиля (например, «MDLP dev → test»)
- **Report folder path** - полный путь к папке PBIP-проекта. Папка должна содержать `.pbip`, `.Report` или `.SemanticModel`
- **Mappings** - список пар Old GUID → New GUID. Для каждого маппинга:
  - **Type** - выпадающий список: Workspace, Dataflow или Dataset
  - **Old GUID** - старый GUID (который нужно заменить)
  - **New GUID** - новый GUID (на который заменить)
  - Кнопка **⇄** - поменять местами Old GUID и New GUID
  - Кнопка **✕** - удалить маппинг
  - Валидация: зеленая рамка = корректный GUID, красная = некорректный
- Кнопка **«+ Add Mapping»** - добавить новую пару GUID

Состояние маппингов сохраняется в localStorage браузера и не теряется при перезапуске.

Сервер дополнительно проверяет входные данные: отклоняет одинаковые Old/New GUID, повторяющиеся Old GUID и цепочки, где New GUID одного маппинга используется как Old GUID другого. Цепочки нужно выполнять отдельными запусками Rebind.

### Рабочий процесс (две кнопки)

#### Шаг 1 - Scan (Фаза 1, только чтение)

Нажмите **«Scan»**. Сервер запускает фоновый worker, который:

1. Находит все `.tmdl` и `.json` файлы в проекте (исключая `.pbi/`)
2. Для каждого маппинга ищет все вхождения OLD GUID
3. Показывает до 2 строк с совпадениями для каждого файла
4. Проверяет, нет ли NEW GUID уже в проекте (частичная миграция)
5. Отмечает неоднозначные контексты (GUID в нестандартных файлах)
6. Сохраняет результаты для следующего шага

**Фаза Scan не вносит изменений в проект.** Просмотрите технический лог и понятное резюме. Если совпадений нет, Apply останется недоступным.

#### Шаг 2 - Apply (Фазы 2+3, замена и верификация)

После успешного Scan выберите **«Continue with Apply»** в резюме (или кнопку **«Apply»**). Отдельного диалога подтверждения нет: резюме Scan является точкой принятия решения.

Перед запуском сервер проверяет, что путь и маппинги не изменились после Scan и что Apply относится именно к тому Scan, который показан в резюме. Любое изменение формы аннулирует результат Scan (в браузере и на сервере) и требует повторного сканирования. Одновременно может выполняться только одна операция Rebind; это гарантирует файл блокировки `rebind.lock`, который worker держит открытым до конца работы, в том числе после перезапуска сервера.

После продолжения worker:
1. Работает только с файлами из списка Scan. Перед первой записью сверяет каждый файл с отпечатком (SHA-256), сохраненным при Scan. Если файл изменился, исчез или не читается, ничего не записывается, а резюме называет этот файл
2. Заменяет старые GUID файл за файлом. Каждый файл записывается целиком через временный файл и сохраняет свою кодировку (UTF-8 с BOM или без, UTF-16 с BOM). Замены засчитываются только после успешной записи. При первой ошибке записи worker останавливается и сообщает, какие файлы уже изменены, а какие нет
3. Выполняет верификацию: перечитывает каждый файл из списка Scan и все текущие TMDL/JSON файлы проекта. Успех возможен, только если все файлы из списка прочитаны и старых GUID нигде нет. Каждая оставшаяся строка со старым GUID попадает в лог
4. Подсчитывает новые GUID и показывает результаты в техническом логе и итоговом резюме

Если Scan не смог прочитать какой-либо файл или папку (например, файл в неподдерживаемой кодировке), Apply недоступен до исправления и нового Scan.

Если выбрать **«Do not continue»**, страница просит сервер аннулировать Scan. Сообщение «Stopped - nothing was changed» появляется только после подтверждения от сервера; иначе показывается «Stop was not confirmed», Apply остается недоступным, а перед любым Apply нужен новый Scan.

### Индикаторы фаз

Рядом с кнопками Scan и Apply расположены три точки-индикатора:

- **Scan** - синяя при сканировании, зеленая при завершении
- **Replace** - синяя при замене
- **Verify** - зеленая при успешной верификации, красная при ошибке

### Логи Rebind

Подробный журнал Rebind отображается в браузере и хранится в `rebind-status.json` только для текущего состояния операции. Каждая запись статуса содержит идентификатор операции, и ее пишет только процесс, владеющий `rebind.lock`. Непредвиденные ошибки worker дописываются в `logs/rebind-worker-errors.log`. Если worker завершился, не закончив работу, статус помечается как прерванный: при прерванном Apply часть файлов может быть уже изменена, поэтому нужен новый Scan.

### Понятное резюме и решение

Технический лог остается без изменений. После Scan под ним появляется отдельная карточка с количеством просмотренных и затронутых файлов, предполагаемых замен и предупреждений. Пользователь явно выбирает **«Continue with Apply»** или **«Do not continue»**. Если выбрать остановку, Scan остается операцией только для чтения и проект не изменяется. После Apply та же карточка показывает итог замены и верификации простыми словами.

### После Rebind

Откройте отчет в Power BI Desktop и обновите данные чтобы подтвердить соединение с источниками. Панель управления не может проверить живое соединение.

## Как это работает внутри

### Refresh

1. При нажатии **«Start Refresh»** сервер проверяет ID и email и запускает в скрытом фоновом процессе общий runner `runtime\Invoke-RefreshRun.ps1`. Тот же runner использует Claude-скилл `powerbi-chained-refresh`. План (dataflow и семантические модели) передается как закодированный JSON; токен входа и его режим передаются только через переменные окружения процесса, а не в аргументах и не в файле
2. Сервер записывает номер процесса в `refresh-worker.json`. Если процесс неожиданно завершился, вкладка показывает «Worker died» и не блокирует следующий запуск
3. Runner не начинает обновление, если эта модель уже обновляется в службе Power BI или ее обновляет другой запуск (блокировка на модель)
4. Runner параллельно запускает обновление всех dataflow
5. Каждые 30 секунд проверяет статус каждого dataflow через API транзакций. Если статус временно не читается, runner повторяет попытки около 10 минут и только потом пишет `Unknown` (результат не подтвержден), а не `Failed`. Ответ 404 не запускает повторное обновление
6. Перед запуском снимает состояние каждой модели для проверки (`validation\validation.ps1`: конфиг отчета или универсальные проверки)
7. После успешного завершения всех dataflow запускает все семантические модели. Если модель в этот момент уже обновляется по другому запросу (например, его запустил кто-то другой, пока шли dataflow), runner ждет окончания этого обновления и только потом запускает свое, чтобы модель обновилась после всех dataflow. Запрос, отклоненный службой из-за параллельного обновления, повторяется так же, не более 3 раз. В ошибке сохраняется текст ответа службы, а не только «(400) Bad Request»
8. Каждые 30 секунд проверяет каждую модель до отдельного конечного результата, затем снимает состояние моделей снова и сравнивает его с исходным
9. Строит итоговое письмо в `validation\validation.ps1` (`New-ValidationEmailContent`) и при необходимости отправляет его в Power Automate flow через `refresh-email.ps1` (если flow принимает только вошедших пользователей, с токеном Power Automate того же входа). Снимки и сравнение каждой модели лежат в папке запуска как `validation-<n>-before.json`, `validation-<n>-after.json` и `validation-<n>-compare.json`
10. Прогресс записывается в `refresh-status.json`, который читается фронтендом. Журнал и `summary.json` каждого запуска лежат в `%LOCALAPPDATA%\PowerBIChainedRefresh\runs\`, ошибки запуска runner в `logs\refresh-worker-errors.log`

### Rebind - Scan

1. При нажатии **«Scan»** сервер проверяет JSON запроса, PBIP-путь и маппинги, создает подпись запроса и запускает `runtime\Invoke-RebindRun.ps1 -Mode Scan` с новым идентификатором операции; параметры передаются в закодированном JSON. Сервер отвечает только после того, как worker захватил `rebind.lock` и записал статус со своим идентификатором
2. Worker перечисляет TMDL/JSON файлы проекта по буквальным путям (пробелы и квадратные скобки в путях допустимы) и ищет старые GUID
3. Для каждого совпадения записывает файл и все номера строк; для файлов со старыми GUID сохраняет список (путь, SHA-256, размер, кодировка), к которому затем привязан Apply
4. Результаты сохраняются в `rebind-status.json`

### Rebind - Apply

1. При нажатии **«Apply»** страница передает идентификатор просмотренного Scan. Сервер сверяет его, путь и маппинги с текущим статусом и запускает `runtime\Invoke-RebindRun.ps1 -Mode Apply`
2. Worker еще раз сверяет Scan под блокировкой, затем заменяет старые GUID только в файлах из списка Scan (точное совпадение, case-insensitive), сохраняя кодировку каждого файла
3. После замены запускает верификацию: файлы из списка Scan и новый перечень файлов проекта
4. Результаты (какие файлы изменены, сколько замен записано, какие файлы не записаны, все оставшиеся строки) записываются в статус

### Rebind - профили

Сервер проверяет весь список профилей перед сохранением (только поля `name`, `reportPath`, `mappings` с `type`, `fromId`, `toId`; без управляющих символов; уникальные имена) и заменяет `rebind-profiles.json` атомарно. Отклоненное или прерванное сохранение оставляет прежний файл без изменений. Черновик с пустой папкой или неполным GUID сохранить можно. Страница не использует сохраненные идентификаторы строк: при загрузке каждая строка получает новый внутренний идентификатор, а обработчики событий подключаются без вставки сохраненных значений в код. Если файл профилей не читается, сохранение в интерфейсе отключено, чтобы не перезаписать его.

## Настройка таймингов

### Refresh: интервал проверки статуса (сейчас 30 секунд)

В `runtime\refresh-engine.ps1` найдите строку:
```powershell
$script:RefreshPollSeconds = 30
```
Замените `30` на нужное значение. Интервал общий для dataflow и семантических моделей.

### Refresh: максимальное время ожидания (сейчас 11 часов)

В том же файле найдите строку:
```powershell
$script:RefreshBudgetHours = 11
```
Замените `11` на нужное количество часов. Незавершенные элементы получают Failed.

### Rebind

Таймингов нет - операции выполняются локально без задержек. Время зависит от размера проекта и количества файлов.

### Важно

После редактирования необходимо перезапустить сервер (закрыть окно панели или консоль и снова запустить ярлык).

## Секреты и публикация

URL flow Power Automate в `REFRESH_EMAIL_WEBHOOK_URL` при настройке trigger **Anyone** работает как пароль: любой, у кого он есть, может вызвать flow. При **Any user in my tenant** или **Specific users in my tenant** одного URL недостаточно, нужен вход в ваш tenant, но URL все равно не публикуйте. Храните его только в пользовательской переменной среды (ее задает `setup.bat`). Не добавляйте его в код, профили, README, issues или письма. Если URL раскрыт, сразу пересоздайте trigger URL в Power Automate и запустите `setup.bat` с новым URL.

Локальные профили, пути к PBIP-проектам, ID рабочих областей, dataset и dataflow, адреса получателей, логи и статусы исключены через `.gitignore`. Каждый пользователь создает свои профили в интерфейсе; они хранятся рядом с приложением. Перед публикацией копии запустите `release-check.ps1` (он есть в публичной копии) и проверьте `git status`. Подробности в `SECURITY.md` публичной копии.

## Планы разработки

Направления, в которых развивается панель. Это не обязательства по срокам, и ничего из текущего поведения не будет удалено.

**Выбор рабочей области и семантической модели по названию (сделано, 2026-11-19).** На вкладке Refresh рабочая область, отчет, семантическая модель и dataflow выбираются поиском по названию, а не по GUID. На вкладке Partition Refresh так же выбираются рабочая область и модель. Профили по-прежнему хранят ID, а названия сохраняются рядом для отображения.

**Автоматическое определение dataflow (сделано, 2026-11-19).** При выборе отчета или модели по названию связанные с ней dataflow находятся по lineage и добавляются в список; лишние можно убрать. Если модель читает напрямую из базы или файла, список пустой, и обновляется только модель.

**Переработка оформления (сделано, 2026-11-19).** Светлая тема и две панели: слева настройки профиля, справа запуск, ход обновления и лог; на узком экране они идут друг под другом. У каждой вкладки свой цвет акцента, шрифты системные. Функциональность при этом не изменилась.

**Ручной ввод идентификаторов сохранен** в свернутом разделе **IDs and manual entry** - он остается запасным вариантом, когда списки недоступны; убирать его не планируется. Списки показывают только те рабочие области и модели, к которым у вас есть доступ, поэтому ручной ввод остается нужен и при ограниченных правах.

## Типичные проблемы

| Проблема | Решение |
|----------|---------|
| Браузер открывается, но страница не грузится | Подождите 5 секунд - сервер запускается не мгновенно. Обновите страницу |
| «Not Authenticated» на вкладке Refresh | Нажмите «Authenticate for Refresh» и завершите вход по коду из консоли |
| Аутентификация недоступна, но нужен только Rebind | Ничего устанавливать не нужно - перейдите на вкладку Rebind |
| Ошибка «Dataflow refresh FAILED» | Проверьте роль в рабочей области (нужен Member или выше). Проверьте правильность ID |
| Ошибка 404 или UnknownError | Dataflow или Dataset не найдены. Проверьте ID в профиле |
| Код устройства не появляется | Проверьте интернет-соединение. Запустите `setup.bat -CheckOnly`: он покажет, установлен ли MSAL.PS |
| `setup.bat` пишет Not ready | Причины перечислены под словами Not ready. Исправьте их и запустите `setup.bat` еще раз |
| Вход сертификатом не проходит | Запустите `setup.bat -CheckOnly`: он покажет, найден ли сертификат и его ключ. Если сертификат найден, проверьте, что его открытая часть загружена в регистрацию приложения и что приложение участник рабочей области |
| Refresh: статус «Starting...» или «Worker died» | Runner не запустился или остановился. Проверьте `logs\refresh-worker-errors.log` и журнал последнего запуска в `%LOCALAPPDATA%\PowerBIChainedRefresh\runs\` |
| «A refresh is already running» | Дождитесь завершения текущего обновления. Если процесс обновления уже завершился, кнопка снова доступна без перезапуска сервера |
| «...is already refreshing in the Power BI service» или «...is already active» | Модель уже обновляется в службе или другим запуском (например, через Claude). Дождитесь окончания |
| Статус `Unknown` у dataflow или модели | Статус не удалось прочитать около 10 минут. Обновление могло завершиться: проверьте историю обновлений в Power BI. Модель после такого dataflow не запускается |
| Email warning: webhook not configured | Запустите `setup.bat` и вставьте URL flow, затем перезапустите панель; либо включите Dry run |
| Refresh успешен, email завершился ошибкой | Результат Refresh сохранен. Проверьте URL trigger и историю запусков flow; ошибка письма намеренно не меняет результат обновления |
| Email: `The flow refused the signed-in call (HTTP 401/403)` | Flow не принял вход. Проверьте **Who can trigger the flow?**: при **Specific users in my tenant** в списке должен быть пользователь, который вошел в панель, или приложение сертификата |
| Email: `a Power Automate token could not be obtained` | Вход по коду устройства: войдите заново на вкладке Refresh. Если не помогло, tenant не выдает этому входу токен Power Automate без согласия администратора: переключите trigger на **Anyone**. Вход по сертификату: приложению может понадобиться разрешение на Power Automate или исключение в политике tenant |
| Email: `URL is not an HTTPS Power Automate address` | Flow требует вход, а URL в `REFRESH_EMAIL_WEBHOOK_URL` не похож на адрес Power Automate, поэтому токен не отправлен. Скопируйте URL trigger заново и запустите `setup.bat` |
| Rebind: Scan не запускается | Проверьте консоль сервера и убедитесь, что выбрана папка PBIP с `.pbip`, `.Report` или `.SemanticModel` |
| Rebind: кнопка Apply неактивна | Выполните Scan и используйте «Continue with Apply» в резюме. Если путь или GUID изменены после Scan, сканирование нужно повторить |
| Rebind: ошибка про chained mappings | New GUID одного маппинга совпадает с Old GUID другого. Разделите замену на два отдельных запуска |
| Rebind: GUID не найден при сканировании | Проверьте правильность GUID и что проект действительно PBIP (с файлами .tmdl) |
| Rebind: после Apply старые GUID остались | Проверьте логи - там указано в каких файлах и строках остались GUID |
| Порт 8765 занят | Закройте другой экземпляр или запустите `powershell -ExecutionPolicy Bypass -File .\server.ps1 -Port 8877`. Интерфейс автоматически использует текущий адрес и порт |
| Иконка вкладки браузера пустая | Нажмите Ctrl+Shift+R для очистки кэша браузера |
| MSAL.PS не установлен | Он нужен только для Refresh. Запустите `setup.bat` еще раз |
